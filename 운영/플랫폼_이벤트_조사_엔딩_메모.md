# 운영 플랫폼·이벤트·조사·엔딩 메모

> **문서 성격:** 운영진 내부 메모. 러너 공개 문서가 아님.
> **운영 전제:** 1인 총괄 (MPC 지원 인력 없음), 러닝 기간 2~4주.
> **러너 공개용 분리:** 확정 후 `플랫폼_안내`, `전투_안내`, `조사_안내`, `이벤트_참여_안내`, `개인_엔딩_제출_안내`로 분리.

---

## 1. 운영 전제와 제약

### 1.1 운영 인력

- **총괄: 1인** (이전 기수 MPC 지원진 부재)
- 보조 인력 부재로 인해 **자동화·반자동화 의존도**를 높여야 함
- 자동화 후보: 개인웹 기능 강화, 디스코드 봇 (Claude Code/Codex로 바이브 코딩)

### 1.2 러닝 기간

- 최소 2주 / 최대 4주
- 사건과 서사 영향 주기를 이 기간에 맞춰 배분해야 함
- 매일 큰 사건이 터지면 **2주차에 운영자가 소진됨**

### 1.3 1인 운영의 위험 요소

| 위험 | 영향 |
| --- | --- |
| 매일 큰 사건 발생 | 운영자 소진, 후반 진행 불가 |
| 공식 반영 지점 과다 | 매 채팅 확인 부담 |
| 분쟁·갈등 중재 부담 | 운영자 멘탈 소모 |
| 시스템 복잡성 | 정산·계산 실수 증가 |
| 비공개 정보 관리 부담 | 일관성 유지 어려움 |

---

## 2. 핵심 운영 철학

> **디스코드는 흐른다. 웹은 남긴다.**
> **러너는 매일 놀 수 있다. 세계는 매일 크게 바뀌지 않는다.**
> **운영자는 모든 대화를 읽는 사람이 아니라, 공식 반영 지점을 관리하는 사람이다.**

이 세 문장이 1인 운영의 전체 원칙이다.

---

## 3. 플랫폼 결정

### 3.1 권장 구조

> **디스코드 메인 + 개인웹**
> 마스토돈은 선택형 또는 제외

### 3.2 디스코드 메인 선택 이유

- 채널 구조로 도시 공간 구현이 직관적
- 채팅 중심 캐어필 가능 (그림 부담 낮음)
- PARAGON vs LIMEN 상시 대립 표현 자연스러움
- 진영별 작전실, 소문방, 뉴스 피드 분리 용이
- 디코봇 자체 제작으로 자동화 확장 가능

### 3.3 디스코드의 단점과 대응

| 단점               | 대응                         |
| ---------------- | -------------------------- |
| 대화가 너무 빨리 흐름     | 활성 구역 주간 2~3개 제한, 챕터 단위 진행 |
| 접속 시간 많은 러너에게 쏠림 | **반응 윈도우 보장** (5.4 참조), 주간 요약 제공 |
| 늦은 러너가 끼기 어려움    | 도시 브리핑·요약 채널 제공, **반응 윈도우** 안의 시점 모호화 |
| 운영자 피로           | A/B/C 채널 등급, 공식 반영 지점 최소화  |

### 3.4 마스토돈 선택형 운영

필수 플랫폼에서 제외. 다음 용도로만 선택적 운영.

- 커뮤 홍보 계정
- 분위기용 공개 계정
- 외부 아카이브
- 종료 후 후일담·로그 보관

### 3.5 개인웹의 역할

복잡한 시스템 전부를 웹이 담당. **1인 운영의 핵심 자동화 기반.**

| 영역 | 웹이 담당 |
| --- | --- |
| 신청·캐릭터 | 신청서, 프로필, 진영, 등급, 등록 상태 |
| 상태 관리 | 체력, 정신력, 부상, 상태이상, 감시도, 아이템 |
| 전투·조사 | 신청, 처리, 결과 기록, 정산 |
| 세계 상태 | 시민 여론 4변수, 도시 안정도, 진실 공개도 |
| 기록 | 공지 아카이브, 사건 파일, 뉴스 피드 |
| 엔딩 | 공통 엔딩 변수, 개인 엔딩 제출 |

## 4. 디스코드 채널 등급 구조

### 4.1 A등급 — 운영자 필수 확인 (최소화)

`#공지` · `#운영문의` · `#신청·정산` · `#메인이벤트` · `#전투진행` · `#조사진행`

**원칙:** A등급 채널을 적게 둘수록 운영 피로가 줄어든다.

### 4.2 B등급 — 가끔 확인 (분위기·떡밥 체크)

`#주요장소-채널들` · `#진영-라운지` · `#익명-소문방` · `#뉴스피드` · `#이벤트-대기실`

**원칙:** 놓쳐도 공식 진행이 무너지지 않게 둔다.

### 4.3 C등급 — 확인 불필요 (러너 자율)

`#잡담` · `#짤·이미지` · `#오너대화` · `#관계모집` · `#비공식대련` · `#일상`

**원칙:** 매일 확인하지 않아도 되게 둔다.

### 4.4 공식 반영 분리 공지 (러너 안내용 초안)

```md
상시 역극 채널의 대화는 캐릭터 간 관계 형성과 일상 연출을 위한 공간입니다.
도시 상태, 세력 관계, 감시도, 부상, 아이템, 메인 사건 결과에 영향을 주는
행동은 공식 진행 또는 시스템 신청을 통해 반영됩니다.
```

**큰 사건 주기: 2~3일 간격.** 그 사이는 반응 윈도우 + 일상 RP.

### 5.2 4주 표준 러닝 모델

| 주차 | 내용 |
| --- | --- |
| 1주차 | 프롤로그, 도시 적응, **CH.1 튜토리얼 이벤트**, **반응 윈도우 (60~72시간)** |
| 2주차 | 일상·관계 형성, **CH.2 조사 이벤트**, **반응 윈도우**, 시민 여론 변동 시작 |

**큰 사건 주기: 주 1~2회.** 챕터 사이는 충분한 반응 윈도우.

### 5.3 운영자 휴식 보장

- 매주 1일은 **공식 이벤트 없는 휴식일** 지정
- 매일 특정 시간대 (예: 02:00~10:00)는 **운영 응답 없음** 공지
- 큰 전투 다음 날은 **반응 윈도우 (5.4 참조)** 로 잡고 신규 사건 없음
- 운영자의 컨디션 난조 시 챕터 일정 1일 연기 가능 공지 미리 둠

### 5.4 반응 윈도우 — 비동기 시간 보장 장치

디스코드의 실시간성 단점을 잡는 핵심 장치. **이벤트 직후 일정 기간 동안 모든 러너의 반응을 동등하게 취급.**

> 러너 공개용 상세 가이드는 [[비동기_반응_기간_보장]] 참조.

#### 5.4.1 왜 필요한가

큰 이벤트가 22시~24시에 진행되면 접속 가능한 러너만 실시간 참여. 다음 날 아침 접속한 직장인·학생 러너는 "이미 끝난 영화에 대한 후기"만 RP하게 됨. 반응 윈도우는 이 격차를 메운다.

#### 5.4.2 기본 구조 — 반응 윈도우만 운용

가장 단순한 1인 운영 친화적 방식. 메모 표준으로 채택.

- 큰 이벤트 종료 직후 **48~72시간**을 반응 윈도우로 지정
- 이 기간의 모든 RP는 **"사건 직후 같은 시점"** 으로 간주
- 시간 순서에 상관없이 후폭풍 RP가 동시 진행됨
- 운영자는 공지만 하면 됨, 별도 처리 없음

#### 5.4.3 반응 윈도우 공지 템플릿

```md
[CH.1 잔광 경보 — 반응 윈도우]

종료 시각: 5월 21일 24:00
반응 윈도우: 5월 22일 09:00 ~ 5월 24일 09:00 (48시간)
결과 카드 공개: 5월 22일 22:00

이 기간의 모든 RP는 "사건 직후"로 취급됩니다.
부상 상태, 진영 갈등, 관계 변화 등 후폭풍 RP를 자유롭게 진행해 주세요.
시간 순서가 어긋나도 문제없습니다.
다음 이벤트는 5월 25일 22:00 시작 예정입니다.
```

#### 5.4.4 확장: 결과 카드 단계별 공개 (선택 사항)

여유가 있을 때만 적용. 정보가 단계별로 풀려서 추리·조사 단서로도 활용 가능.

| 시점 | 내용 | 채널 |
| --- | --- | --- |
| 이벤트 종료 직후 | 1차 속보 (사건 개요 1~2줄) | #뉴스피드 |
| 다음 날 정오 | 2차 상세 발표 (관리감시국 공식 브리핑) | #뉴스피드 |
| 24시간 후 | 3차 후폭풍 정보 (의혹·추가 단서) | 웹사이트 사건 파일 |
| 48시간 후 | 여론 변동 결과 카드 | 웹사이트 도시 상태 |

#### 5.4.5 분위기 통제 규칙

반응 윈도우가 작동하려면 러너들이 약속을 지키게 분위기를 만들어야 함.

- **실시간 참여 러너에게 사전 안내** — "반응 윈도우 시작 전까지 큰 관계 변화 RP는 자제"
- **확정 결과는 운영자 발표 후에만** — 결과 카드 공개 전에는 추측·반응만
- **늦은 러너용 핀 메시지** — "사건 요약 + 현재 분위기 3줄"을 디스코드 채널 핀에 고정
- **반응 윈도우 종료 시점 명확화** — "여기서부터는 현 시점 RP" 라인을 운영자가 그어줌

#### 5.4.6 채널 분리 (선택 사항)

서버 구조에 여유가 있으면 채널을 챕터별로 분리.

- `#실시간-이벤트-CH1` — 사건 당일 실시간 진행만
- `#사건후폭풍-CH1` — 반응 윈도우 기간 전용 (종료 후 보관)
- `#일상-카페` — 후폭풍 기간 종료 후 일상 복귀

장점: 채널 토픽으로 시점 표시 가능, 종료 후 아카이브 정리 쉬움
단점: 챕터마다 채널 생성·정리 작업 필요

#### 5.4.7 시점 태그 (러너 자율 옵션)

반응 윈도우 안에서 러너가 자율적으로 시점을 표시하고 싶을 때 사용.

```
[사건 중]  — 실시간 이벤트 중
[직후]     — 사건 종료 ~ 다음 날 아침
[1일차]    — 사건 다음 날
[2일차]    — 그 다음 날
[현재]     — 반응 윈도우 종료 후
```

운영자가 강제하지 않음. 러너가 시간선을 명확히 하고 싶을 때만 활용.

## 6. 이벤트 구조

### 6.1 이벤트 4유형 (앞서 확정)

탈취전 / 구출전 / 방어전 / 색출전. 챕터별로 PARAGON·LIMEN의 공격·방어 역할이 뒤바뀌도록 배치.

### 6.2 이벤트 템플릿

```md
# 이벤트명
## 공개 공지
## 참여 가능 진영
## 진행 기간
## 활성 구역
## 기본 목표 (진영별)
## 선택 행동
## 조사 가능 항목
## 전투 발생 조건
## 획득 가능 단서 (공개·조건·핵심)
## 감시도 변동 기준
## 시민 여론 변동 기준
## 성공·부분성공·실패 결과
## 운영진 비공개 메모
## 후속 이벤트 연결
```

### 6.3 이벤트 설계 체크리스트

- 러너가 무엇을 할 수 있는가
- PARAGON·LIMEN 각각의 목표가 명확한가
- 관리감시국은 어떤 압박을 주는가
- 시민 피해 반영 방식이 있는가
- 감시도·여론 변수가 어떻게 움직이는가
- 실패해도 다음 이야기로 이어지는가
- 세계관 비밀이 너무 빨리 풀리지 않는가
- **운영자가 하루 단위로 처리 가능한 분량인가**

## 7. 첫 전투 — 튜토리얼 이벤트

### 7.1 첫 전투의 목적

이기는 전투가 아니라 **배우는 전투**.

- 전투 시스템 체험
- 아이템 사용 흐름 확인
- 감시도 반영 체험
- 조사·전투 연결 확인
- 진영별 행동 방식 체험
- **운영자가 정산 부담을 점검할 기회**

### 7.2 추천 형식 — "제한 교전 구역"

가칭: **잔광 경보**

- 관리감시국 감시망 또는 잔명 감지망 이상 발생
- PARAGON: 현장 통제·민간 보호
- LIMEN: 감시망 틈을 노려 로그 탈취·억류자 정보 확보
- 치명상 금지, 사망 판정 없음
- 중상은 사전 동의 필수
- 감시도 변동 작게 적용
- 보상 차이 작게

### 7.3 구역 예시

| --- | --- |
| 대피로 | 민간인 보호, 구조, 추격 |
| 감지탑 주변 | 장비 보호, 해킹, 교란, 로그 탈취 |
| 차폐 지하로 | 은신, 회수, 1대1 제한 교전 |

## 8. 전투 분류와 1대1 개방 정책

### 8.1 전투 2종

| 종류 | 사용처 | 특징 |
| --- | --- | --- |
| 서사 전투 | 훈련 대련, 라이벌 충돌, 감정 대립 | 운영 개입 최소, 장면 중심, 감시도·보상 약함 |
| 시스템 전투 | 메인 이벤트, 진영전, 보스전 | 공식 기록, 감시도·부상·보상·여론 영향 |

### 8.2 1대1 개방 일정

> **첫 튜토리얼 이벤트 완료 후 → 신청제로 제한 개방**

### 8.3 1대1 신청제 조건

- 양측 동의 필수
- 신청제 (주간 신청 횟수 제한 — 수치 미정)
- 전투 목적·장소·공개 여부·부상 허용 범위 사전 작성
- 감시도 반영 여부 선택
- 공식 보상은 없거나 소량
- 사망·불구·납치·장기 감금은 별도 동의

### 8.4 감시도 반영 기준

```md
공개 장소 / 능력 사용 / 민간 피해 / 추적 가능한 로그가 남는 전투
→ 감시도 반영

차폐 구역 / 합의 대련 / 비공식 훈련
→ 감시도 반영 약함 또는 없음
```

### 10.1 자동화 단계별 계획

| 단계 | 우선순위 | 구현 방식 |
| --- | --- | --- |
| 1차 (오픈 전 필수) | 신청서, 캐릭터 프로필, 체력·상태, 전투 결과 기록 | 웹 폼·DB |
| 2차 (오픈 직전) | 감시도, 아이템, 사건 파일, 뉴스 피드 | 웹 페이지 |
| 3차 (러닝 중) | 도시 상태 대시보드, 여론 변수 시각화 | 웹 페이지 |
| 4차 (확장) | 디스코드 봇 연동 (조회·신청 카드) | Claude Code·Codex |
| 5차 (장기) | 봇 자동 정산, 문서 검색, AI 요약 | 봇 + AI API |

### 10.2 디스코드 봇 구조 (장기 구상)

```
Discord → 디코봇 → 웹 백엔드 API → DB·문서
```

**원칙:**
- 봇은 DB 직접 수정 금지 (반드시 웹 API 경유)
- 모든 수정은 로그 기록
- 러너용 봇은 운영진 비공개 문서 접근 불가
- **AI는 설정 창작자가 아니라 검색·요약 보조**
- 모르는 정보는 "모른다"고 답하게 (추측 금지)

### 10.3 MVP 봇 명령어

```text
/내정보       — 본인 캐릭터 상태 조회
/감시도       — 현재 감시도 단계 조회
/도시상태     — 4변수 현황 조회
/아이템       — 보유 아이템 목록
/공지         — 최근 공지 링크
/문서검색     — 세계관 문서 검색 (공개만)
/전투신청     — 1대1 전투 신청 카드 생성
/조사신청     — 조사 신청 카드 생성
```

### 10.4 봇 개발 시 주의사항

- 초기에는 AI 기능 없이 단순 조회·신청만 구현
- AI 기능 추가 시 **세계관 일관성 검증 필수**
- 봇이 운영자 권한을 갖지 않게 (승인은 운영자 수동)
- 봇 다운 시 수동 대체 가능한 흐름 유지

### 10.5 봇 없이 시작할 경우

- 웹 페이지의 폼만으로도 운영 가능
- 디스코드는 알림·문의·이벤트 보조용으로 한정
- 봇은 2차 러닝 또는 4주차 러닝부터 시도

## 12. 엔딩 시스템

### 12.1 캐치프레이즈

```md
뉴 센티넬은 이전과 같은 도시로 돌아갈 수 없다.
그리고 당신도, 이전과 같은 사람으로 돌아갈 수 없다.
```

### 12.2 엔딩 분기 변수

**공개 운영 변수 (이미 확정된 4변수):**
- 뉴 센티넬 안정도
- PARAGON 신뢰도
- 감시 체계 신뢰도
- LIMEN 영향력

**비공개 엔딩 플래그 (이번 논의에서 추가 제안):**
- **진실 공개도**
- **시민 피해도**

> ※ 비공개 2변수 추가는 [[감시도와 여론 시스템]]과 정합성 확인 필요.

### 12.3 엔딩 패밀리 6종

| # | 엔딩명 | 조건 | 핵심 |
| --- | --- | --- | --- |
| 1 | PARAGON 승리 — 개혁된 질서 | 신뢰도↑ + 안정도↑ + 진실 공개도 중간↑ | 살아남았지만 내부 개혁 피할 수 없음 |
| 2 | PARAGON 승리 — 통제된 평화 | 신뢰도↑ + 감시 신뢰도↑ + 진실 공개도↓ | 강압적 승리, 안도와 공포 공존 |
| 3 | LIMEN 승리 — 폭로와 해방 | LIMEN 영향력↑ + 진실 공개도↑ + 시민 피해도↓ | 진실 공개, 시민사회 전면 |
| 4 | LIMEN 승리 — 균열과 무정부 | LIMEN 영향력↑ + 안정도↓ + 시민 피해도↑ | 감시 해체했지만 자유는 오지 않음 |
| 5 | 공동 폭로 — 불완전한 재건 | 양측 영향력 일정 이상 + 진실 공개도↑ | 누구도 완전히 이기지 못함 |
| 6 | 진실 은폐 — 불안정한 평화 | 안정도↑ + 진실 공개도↓ + 감시 신뢰도 유지 | 평화롭지만 사라진 기록을 기억하는 자들 |

### 12.4 엔딩 문구 변형 예시

각 엔딩의 핵심 정서를 담는 1~2줄 문구를 미리 준비.

```md
[1] 도시는 지켜졌다. 그러나 지켜진 도시가 누구의 손으로 유지되었는지, 모두가 보게 되었다.
[2] 도시는 조용해졌다. 그러나 그 침묵이 평화인지, 통제인지 누구도 쉽게 말하지 못했다.
[3] 도시는 진실을 알게 되었다. 그러나 진실을 안 도시가 더 나은 도시가 되는 데에는, 더 많은 시간이 필요했다.
[4] 도시는 감시에서 벗어났다. 그러나 감시가 사라진 자리에 곧바로 자유가 피어나지는 않았다.
[5] 누구도 완전히 이기지 못했다. 그래서 도시는 처음으로, 하나의 이름이 아닌 여러 목소리로 미래를 말하기 시작했다.
[6] 도시는 아무 일도 없었다는 듯 불을 밝혔다. 그러나 그 빛 아래에서, 사라진 기록을 기억하는 사람들은 사라지지 않았다.
```

### 12.5 개인 엔딩 제출 항목

```md
1. 생존 상태 (생존/사망/실종/행방불명/수감/은둔)
2. 최종 소속 (PARAGON 잔류·이탈 / LIMEN 잔류·이탈 / 무소속 / 시민사회 / 기타)
3. 등록·감시 상태 (정상·강화·삭제·조작·미등록·추적·보호관찰)
4. 캐릭터가 얻은 것
5. 캐릭터가 잃은 것
6. 마지막으로 선택한 신념
7. 주요 관계 후일담
8. 공통 엔딩 이후의 삶
```

**검수 범위:** 사망, 장기 수감, 중대 세계관 변화, 핵심 NPC 처분은 운영진 확인 필요.

## 13. 결정 상태 정리

### 13.1 확정에 가까운 운영 방향

- 복잡한 시스템은 개인웹 담당
- 공식 결과는 웹에 기록
- **디스코드 메인 + 개인웹 구조** (2026-05-21 확정)
- 마스토돈은 선택형 또는 제외
- 디스코드 상시 대화와 공식 진행 분리
- A/B/C 채널 등급 구조
- 첫 전투는 튜토리얼형 제한 교전
- 1대1 전투는 튜토리얼 후 신청제 제한 개방
- 이벤트·조사 템플릿화
- 엔딩은 멀티엔딩 패밀리 구조
- **운영자 휴식 보장 (주 1일 휴식, 매일 응답 없는 시간대)**
- **반응 윈도우 시스템 (이벤트 후 48~72시간 비동기 시점 보장)**

### 13.2 권장 사항

- 활성 구역 주간 2~3개로 제한
- 주간 도시 브리핑 운영
- 문의는 DM보다 전용 채널·양식
- 디코봇은 처음에는 AI 없이 단순 조회 기능부터
- AI 기능은 문서 검색·요약·브리핑 초안에 한정
- 조사 데이터 초기는 스프레드시트, 정식은 웹 DB
- **결과 카드 단계별 공개는 선택 사항** (1차 러닝에서는 단순 윈도우만 운용)
- **늦은 러너용 핀 메시지** (사건 요약 + 현재 분위기) 활용

### 13.3 미결정 사항

- 디스코드 채널 수와 카테고리 구조 세부
- 첫 이벤트 정확한 제목·위치
- 1대1 전투 주간 신청 제한 수
- 감시도 반영 전투 세부 기준
- 디코봇 개발 시점 (1차 러닝 전 vs 2차 러닝 이후)
- 엔딩 패밀리 수치 조건 세부
- 개인 엔딩 검수 범위
- 비공개 엔딩 플래그 2개 추가 확정 여부
- **반응 윈도우 길이 세부** (48시간 vs 60시간 vs 72시간)
- **반응 윈도우 채널 분리 적용 여부** (서버 구조 부담과 trade-off)
